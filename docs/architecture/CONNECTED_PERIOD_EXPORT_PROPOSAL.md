# Connected selected-period export

Date: 2026-10-18
Status: Implementation approved by Product Owner (DEC-037); delivery verification pending
Phase: 7C.3 (no Phase 7C.4 transition)

## Scope and evidence

PR-002, PR-010, PR-015 and backlog 10.1 require complete selected 26–25 period
CSV, excluding archived transactions. Accepted local CSV delivery remains accepted;
this gap concerns connected mode only. The integration plan explicitly disallows
exporting only one page of history.

Source inspection:

- `frontend/src/lib/reportCsv.ts` already supplies 14 columns, UTF-8 BOM,
  CRLF, quoted/escaped fields, formula-prefix protection and resolved pocket/category
  labels. Reports names the file with the selected period boundaries.
- `frontend/src/lib/api/transactionRead.ts` deliberately validates one page only.
- `backend/src/routes/transactions.ts` lists 50 rows by default, at most 100,
  using offset pagination. Count and rows are separate reads. Ordering is date,
  local time, created timestamp; there is no final unique-ID tie breaker.
- The transaction contract has no complete-export endpoint or cross-request snapshot.

Therefore a client loop is not a consistent export: inserting a newer row between
pages can repeat a row; deleting/archiving an earlier row can skip one. Edits can
change ordering or period membership. Comparing counts or deduplicating IDs cannot
prove completeness. This is a source-derived risk, not a claimed runtime test.

## Approved bounded extension

Add an authenticated read-only `GET /v1/transactions/export` with required
`startDate` and `endDate`, validated as one exact inclusive 26–25 budget period.
Reject unsupported query parameters; do not inherit history search/type/pocket
filters. Existing history pagination and financial-write contracts stay unchanged.

Return a complete CSV attachment generated by the backend from one consistent
database snapshot, including owner-scoped pocket/category label resolution in that
same snapshot. Prefer one joined SELECT; if multiple queries are required, use an
explicit read-only repeatable-read transaction. Sort date/time/created timestamp
descending, then unique transaction ID descending. Exclude archived and deleted
transactions and all other owners' data. No allocation creation or balance mutation.

Preserve the current 14 column names/order, integer rupiah, BOM, CRLF, escaping,
formula protection, fallback labels and period-based filename. Labels represent
names at export time, not historical name snapshots. No new financial columns,
backup/restore semantics or dependency. Send `Cache-Control: no-store` and the CSV
content type/disposition; authenticate before producing content.

Frontend should wait for the complete successful response before starting a file
download. Network/authentication failures must show failure without saving a partial
CSV. Capture the selected period at click time, disable repeated dispatch while busy,
and never silently fall back to local data or the visible history page. A direct
empty export can return headers only; normal UI preserves its no-data guidance.

No silent row cap. Before implementation finalize resource limits/timeouts and error
behavior in the contract: an oversized or failed export must fail explicitly, never
claim a truncated result is complete. Streaming/background export is outside this
bounded proposal unless resource verification demonstrates a need for refinement.

## Verification required after approval

1. Contract/error schemas and exact response headers, then backend implementation.
2. More than 100 rows; all three types; exact boundary dates; archived/deleted and
   cross-owner exclusion; tied timestamps; unchanged financial state after GET.
3. Concurrent edits/creation/archive during export prove snapshot behavior, including
   labels. Count comparison alone is not sufficient evidence.
4. CSV adversarial quotes, commas, newlines, Unicode and formula prefixes; filename,
   BOM, all columns and precise amounts; empty period; invalid period and no session.
5. Frontend transport, failed/interrupted download and repeated click behavior;
   type-check, both builds, connected browser console/download verification.
6. PO manual review remains separate from automated verification.
