# Phase 7C.3 — Batch terminal resolution backend

Date: 2026-10-17
Authority: DEC-036, approved through PO continuation after the explicit proposal.
Scope: backend contract and recovery only; same Phase 7C.3, no new phase/cutover.

## Delivered

- `POST /v1/transactions/batch/resolve-attempt` shares exact batch shape validation
  and authenticates owner/CSRF before resolving the original root/item hashes.
- All root/item mutation locks use the existing deterministic order shared with
  single-create and batch execution. One SQL transaction persists terminal outcome
  and remaining permanent fences; conflict or corrupt item rolls back new fences.
- Committed roots return validated historical acknowledgements. Absent roots stop
  with explicit ordered item results, including any already committed items. No
  financial rows are changed, undone or generated by resolution.
- All/some/no items previously committed, pre-cancelled items, lost-response retry,
  later transaction changes, owner isolation and concurrent submit/stop are covered.
- Existing create/batch nullable categoryId/note documented, preserving original
  hashes and topology. No migration, dependency or current-balance calculation added.
- Historical note compatibility matters: single-create preserves raw note whitespace,
  batch-created items trim. A matching historical acknowledgement can contain either;
  recovery does not rewrite either form or normalize the original request hash.
